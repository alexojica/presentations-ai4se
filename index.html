Benchmark failure taxonomy

A completion can look plausible but still violate the API surface of the requested library version.

Scorer labelMeaning in the benchmark scorer
correctExtracted API path equals the target API path.
wrong_api_validPredicted API exists in the target version, but is not the target API for the row.
phantomResolved predicted API does not exist in the API compatibility matrix.
anachronisticPredicted API exists in some version, but not in the requested target version.
no_apiNo API-like span is extracted from the generated completion.

Important distinction

  • API-path taxonomy and signature/argument taxonomy are scored separately.
  • For arguments, extra parameters are classified as target-version valid, anachronistic, or phantom using the signature matrix.
  • unresolvable is used after API-span extraction when the scorer cannot reconstruct a canonical full API path from the target prefix/leaf alignment.
Timing: 1 minute. These definitions are checked against src/eval_benchmark/score.py and analysis.py. Do not use informal definitions that drift from the scorer.

What LibEvolutionEval told us

Original benchmark result

  • Broad LibEvolutionEval sweeps plateaued around the baseline: the best overlap-v2 run moved mean id_f1 only 0.7961 -> 0.7974.
  • 1025 / 1055 predictions were string-identical to the baseline in the key overlap-v2 comparison.
  • Only 25 / 1055 benchmark rows involved APIs changed between Torch 2.0.0 and 2.2.0.

Interpretation

  • The score mostly measured general code/API completion and benchmark format behavior, not true version-specific hallucination.
  • The largest fixable mass was on stable common APIs such as tensor conversion, reshape/view, constructors, and reductions.
  • This is why the project moved to diagnostic API-level experiments with target recall, leakage, retention, and paired movement.
Timing: 1 minute. The benchmark was useful because it falsified the first thesis operationalization. It was noisy for the version-specific claim: changed APIs were under-covered, and the observed movement reflected general coding/API selection more than target-version hallucination.

Evaluation measurements

Benchmark tasks

  • T1: code-context completion; main surface for current adapter experiments.
  • T2: API-name identification from benchmark context.
  • T3: signature and parameter recall.
  • The tasks are reported separately because API-name use, API existence knowledge, and signature recall do not collapse into one score.

Movement metrics

  • Target recall: exact target API on target rows.
  • Target leakage: target API emitted on non-target rows.
  • Wins: baseline wrong, adapter correct.
  • Regressions: baseline correct, adapter wrong.
  • Retention: baseline-correct rows that stay correct.
Aggregate exact match is reported, but it is interpreted only after looking at which rows moved and which taxonomy categories changed.
Timing: 1 minute. The wording is deliberately methodological. It explains how I interpret a score increase rather than treating it as self-explanatory.

Training data controls

Rows used in the single-API studies

  • Target-positive rows: realistic code contexts where the correct completion uses torch.compiler.is_compiling.
  • Anchor rows: non-target APIs that the model should continue using correctly.
  • Version text was treated as an experimental variable, not assumed to always help.
  • Task-diverse chat reused the same code examples through several output contracts.

Leakage controls

  • No benchmark rows in the training set.
  • The API identity must appear in the trained output span when testing API-name acquisition.
Timing: 1 minute. This slide distinguishes grounding sources from model inputs. We used API knowledge to build examples, but we do not want the model to solve by copying docs.

Single-API experiment overview

Control 1 Target-only positives Can SFT make the model emit a missing API at all? Yes: FIM/prefix/chat can acquire the target, but positives alone create strong overuse pressure.
Control 2 Target + anchors Can replay rows preserve known APIs and reduce target leakage? Mostly yes: anchors reduce leakage, but in chat they can suppress weak target learning.
Control 3 Staged anchors then target Can an anchor-initialized adapter safely add the target later? It can add the API, but target-only continuation reintroduces leakage unless stopped early.
Control 4 Task-diverse chat Does changing the output contract reduce benchmark-format specialization? Best chat point so far improves over the target-heavy code-gap point, but not every leakage tradeoff.
Readout Broad movement analysis Are gains target knowledge, task alignment, or collateral movement? Use paired wins/regressions, direct target mentions, taxonomy deltas, and per-version slices.

Staged anchor-target training

Interpretation

  • Anchor-only initialization improved broad behavior but kept target rows at 0/12.
  • Target continuation taught the API, up to 10/12.
  • Without active anchor replay during target continuation, leakage and phantom errors increased for aggressive checkpoints.
  • The plotted metrics are aggregate over all Torch version slices in the matched T1/L2 sample.
  • Conclusion: anchors need to remain active while target learning happens.
Timing: 1 minute. This comes immediately after the target+anchor controls because it tests whether anchor behavior survives when the target is added in a second phase.

Current conclusion

What the experiments support

  • LoRA SFT can inject a missing API: target rows moved from 0/12 to 6-10/12 in several controlled runs.
  • Knowledge injection is coupled to task alignment: anchor chat-gap reached +6.34 pp broad EM but only 1/12 target rows.
  • Retention/overuse is the main failure mode: target-only FIM gets 12/12, but leaks on 73.19% of non-target rows and collapses broad EM.
  • Task-diverse chat is promising but bounded: t11 beats the target-heavy code-gap point, while balanced code-gap remains lower-leakage.

Literature alignment

  • LIMA (Zhou et al., arXiv:2305.11206): SFT mainly teaches response style and use of existing knowledge.
  • Gekhman et al. (arXiv:2405.05904) and How do language models learn facts? (arXiv:2503.21676): new facts can increase hallucination and corrupt old memories.
  • LoRA Learns Less and Forgets Less (Biderman et al., arXiv:2405.09673): LoRA trades target acquisition against retention.
  • Gorilla (Patil et al., arXiv:2305.15334): API learning needs explicit API-space grounding and hallucination-aware evaluation.
Timing: 1.25 minutes. This replaces the previous broad evidence slide. The main claim is not that task-diverse chat solved the frontier; it is that knowledge injection, task alignment, and forgetting are empirically entangled and match the literature.

Next experimental controls

Immediate diagnostic experiments

  1. Balanced task-diverse chat: keep target examples fixed, increase active anchors.
  2. Common-gradient task batch: continue the multi-task setup by applying only the shared API-gradient component across task renderings.
  3. Hard-negative task-diverse chat: add close non-target compiler/tracing predicates.
  4. Version-negative rows: teach when the API should not exist.

Checkpoint selection

  1. Use target-only eval only as a cheap first filter.
  2. Broad-evaluate the best target checkpoint plus lower-leakage alternatives.
  3. Select by target rows, direct leakage, wins/regressions, and taxonomy movement.
Timing: 1 minute. The common-gradient item is the `api_common` continuation from the gradient-isolation artifact: render the same API examples across multiple task forms, project away task-format directions, and test whether the remaining shared direction improves target rows without leakage.

The scorer exposes exact API, wrong-valid, phantom, no-API, anachronistic, and signature categories.

Current result

Single-API learning is possible

For torch.compiler.is_compiling, chat SFT moved target rows from 0/12 to 10/12 in the best task-diverse checkpoint.

Research gap

Locality is not solved yet

The same adapters also move many non-target rows, so the next step is reducing leakage and regressions with anchors, hard negatives, and version negatives.
